# 工作台范式与闭环建设

状态：建设规格与实现对照。当前工作区已有首版记忆治理、跨事项召回、采用快照及受控流程接入；存在回归失败，专项测试、首页操作验收与真实跨事项闭环验收待完成。核对日期：2026-09-14。

工作台 = Harness + 记忆系统 + 工作流蒸馏。三者通过真实 FlowERP 交付形成循环：带着已有经验理解现场问题，选择适用流程，在 Harness 约束下交付，保留结果与失败，再把经过验证的经验送回下一次交付。人负责判断和授权，Codex 协助调研、实现及提炼，工作台负责组织执行和保存证据。

## FDE 的价值：把现场问题变成可持续交付的能力

本项目将 FDE（Forward-Deployed Engineering）落实为现场、交付、能力三个相互衔接的循环。建设主线是：**用 Codex，搭建个人 AI 研发工作台；通过工作台组织人与 AI 协同，持续开发 FlowERP。** Codex 是开发伙伴，工作台是组织协作和保存证据的阵地，FlowERP 是接受业务验收的客户产品。

以下以库存问题说明这条主线，属于建设与验收示例，不是已经完成的客户交付记录。

业务人员反馈“页面显示还有库存，订单却下不成功”。学生需要和业务人员一起核对可用库存、已预占数量、失败请求及期望行为，判断问题发生在库存计算、并发预占还是页面展示。Codex 协助查阅源码和梳理证据，人确认业务规则与验收标准，工作台首页的“事项与决策”保存这些判断。这是现场循环的价值：把一句模糊反馈转成有依据、能验证的需求，减少做错需求造成的返工。

确认需要修复预占逻辑后，学生与 Codex 检查工作台能否表达授权写集、执行隔离修改并验证失败时库存不变；缺少的能力先补入工作台，再用于本次 FlowERP 修复。工作台组织执行、保留 Diff 和 Eval，审核者根据业务结果决定接受或返工。这是交付循环的价值：让正确的业务判断落实为可运行、可复验、有人负责的产品变化。完成界面或生成代码，仍需经过库存业务规则的验收。

这次修复还应留下“库存写操作需要事务边界和失败不变性检查”的候选经验，记录来源、适用条件及独立审核；具体检查步骤经试用后成为版本化流程。下一事项处理“订单取消后释放预占”时，学生先判断经验是否适用，明确采用哪个版本，再由工作台组织 Codex 实现并运行该事项自己的 Eval。若复用失败，保留原因、停用或修订流程。这是能力循环的价值：让下一次交付能够使用前一次经过检验的做法，同时允许新证据纠正旧经验。

Harness 使本次交付受控，记忆系统使经验有来源且能被下一事项找到，工作流蒸馏使经验证的步骤能够被明确采用。三者的价值要在后续 FlowERP 交付中体现：需求判断是否更准确，同类失败是否减少，返工和验收耗时是否改善，以及出错时能否追到依据并停止错误复用。应记录真实事项的首次判断、采用理由、失败与修订、业务验收和耗时；目前这些效果仍待测，不能从资产数量或一次测试通过推断提效。

课程按这一因果关系逐步换挡：L01～L03 由学生直接监督 Codex 构建规则、Spec 与解析能力；L04 补齐工作台 V0，并首次由它组织交付 FlowERP；L05～L16 持续用现场问题推动工作台升级，再将能力用于产品交付。学生需要证明自己能判断何时复用、何时拒绝和如何修订，而不是仅展示参考仓库已有功能。

## 三部分的职责

以下为持续建设与验收要求；各项当前实现程度以上述代码对照和验证结果为准。

### Harness：让一次行动受控且可复验

输入包括目标、Spec、授权写集、预算、所采用的记忆快照与流程版本。执行保留工具和状态事件、候选 Diff、Eval 报告、退出码及具名审核。流程建议不得扩大写集、替代业务审批或绕过质量门。

### 记忆系统：让后一次行动能够使用前一次经验

保留三类材料：事项与任务的原始经历；从经历中确认的业务事实、决策理由和失败教训；指向已发布流程版本的程序性记忆。原始证据与提炼结论分别保存，结论始终能够回到来源。

每条可复用记忆至少包含：项目归属、来源事项和任务、证据引用及摘要校验、内容、适用条件、不适用条件、状态、版本、审核记录和替代关系。首版代码采用 candidate、active、superseded、revoked 四种状态。相互矛盾的结论应显式呈现给人判断；过期或撤回的经验保留历史，但不得默认注入新任务。

新事项调研应按项目和适用条件检索，在有限上下文预算内给出召回理由和证据。采用时保存不可变快照；记录未采用理由。检索不到应如实为空。首版已使用标准库 SQLite 与明确关键词，不依赖外部向量服务。

### 工作流蒸馏：将经过检验的做法变成可复用程序

蒸馏对象是解决问题的工程流程，不是模型权重。一次成功可产生候选，不能自动证明普遍有效；失败和返工同样是输入证据。

候选流程至少定义：输入参数、触发条件、前置检查、步骤与依赖、人和 Codex 的职责、授权节点、Eval 入口、输出证据、停止与回退条件、适用边界、来源任务以及版本。原始轨迹应保留，不能只留下成功摘要。

流程发布复用前，需经过候选审核和隔离复验；试用版本在独立事项中显式绑定，仍由既有 Harness 执行。后续验收须同时证明流程被使用、业务增量正确、权限边界未被突破。流程失效时允许停用和新版本替代，历史执行仍指向当时采用的版本。

## 最小可交付闭环

1. 从已验收事项或已接受失败反馈提炼一条有证据引用的候选经验；复用现有任务和 Evolution 标识。
2. 在首页该事项内展示候选经验、适用边界与原始证据，完成具名审核。
3. 在另一事项调研中召回该经验，显示原因；记录采用或不采用及其理由。
4. 从真实修订轨迹提炼一份参数化流程候选，绑定版本、来源及隔离复验结果。
5. 后一事项在确认方案时明确采用流程版本与记忆快照，执行仍经过现有授权、Eval 和验收链。
6. 把复用结果回写为新证据；失败保留并推动修订或停用。首页同一事项内可追到整条因果链。

上述六步已有首版代码对应，但尚未形成通过验收的完整交付。后续先处理无项目事项的回归失败，再补齐记忆存储与状态治理、调研召回与采用快照、流程试用及后续验证的正常与失败路径测试，最后从首页走通真实跨事项验收。每一步都要核对服务、首页交互和持久化，后端接口存在不能代替用户可操作验收。

## 完成验收

以下是待执行的验收场景，不是已经发生的交付或教学证据。

正常路径：事项 A 在库存预占问题中保留失败、修订与通过证据，提炼“库存写操作的事务与失败不变性检查”经验；事项 B 处理订单取消释放预占时召回并采用适用流程，产生新的 ERP 增量。证据必须包含 A 的来源、记忆版本、B 的采用记录、流程执行记录、B 自身的阻断 Eval 和具名验收。

失败路径：尝试跨项目召回、使用撤回记忆、引用被替换的证据、跳过审批或采用不满足前置条件的流程，应被排除或阻断并留下原因。流程在 B 中失败时不得因 A 曾成功而标记通过。重启后应可恢复引用链；发布新版本不得改写旧任务快照。

效果指标包括有效召回与采用、复用成功和失败、返工原因及重复失败是否减少。真实数据产生前一律标为待测，不能用资产数量、模型自述或模拟结果证明系统已经形成持续学习能力。

本规格不改动 16 讲课程合同，不将可选 Harness 驾驶舱升级为必做要求，也不证明学生能力或课程申报条件已达成。
